# DRAFT: diagnostic certification strategy for real-double PSD support

Status: nonbinding test design for `bd-01M0V97EFJ91TKKSH3KH09WMJE`.

The 1.3 quality bar is not “many tests” or a green aggregate suite. Every
advertised capability must have a test that would identify a plausible wrong
implementation, name the violated invariant, and preserve enough evidence to
localize the defect. Public names are deliberately absent until the contract
freezes them.

## 1. Test-design rules

1. Test a mathematical relationship, classification decision, provenance
   claim, or resource boundary—not an implementation detail by itself.
2. Pair each production path with an oracle that does not repeat its decisive
   algorithm whenever practical.
3. Assert typed condition class, stable code, relevant field, and quantitative
   diagnostics. Message fragments are secondary reader-facing checks.
4. Separate source validation from repaired-action validation. A correct
   factor for a clipped matrix does not prove the original matrix was PSD.
5. Compare repeated eigenspaces through projectors/principal angles, not raw
   eigenvector columns.
6. Test sparse non-densification with both structural instrumentation and
   process-level memory evidence; a class assertion alone is too weak.
7. Use deterministic seeds and shrinkable parameter grids. Record a failing
   seed, dimensions, scale, spectrum, thresholds, representation, and route.
8. Keep correctness, performance, installed-consumer, hosted-CI, and exact
   artifact claims separate.

## 2. Oracle hierarchy

Use the strongest independent oracle appropriate to each test:

| Oracle | Best use | Independence requirement |
|:---|:---|:---|
| analytic diagonal/identity result | exact boundaries, zero form, action orientation | production must not route through the same dense kernel |
| constructed orthogonal spectrum | dense singular/repeated spectra | fixture builds `Q diag(lambda) Q^T`; assertions use invariant actions/projectors |
| direct algebraic residual | roots, pseudoinverse, reduction/lift, projectors | computed from original fixture and returned actions, not cached diagnostics |
| small dense base-R/LAPACK eigendecomposition | differential reference for dense or sparse fixtures | test-only densification is explicitly scoped and dimension-bounded |
| graph/connectivity theorem | Laplacian PSD and nullity | graph components computed independently of spectral implementation |
| finite-difference/action probing | operator orientation and block behavior | probe basis and random blocks outside production factor caches |
| high-precision oracle where needed | near-boundary cancellation/conditioning | optional certification tier; record precision and rounding policy |
| mutation operator | prove a test detects a realistic fault | fault is injected at the action/classification boundary and test must fail for the intended reason |

No test may treat “the implementation agrees with itself” as certification.

## 3. Required diagnostic fields on failure

After API freeze, helper assertions should require a typed PSD condition with
at least the frozen equivalents of:

```text
code, field/action, expected, actual,
source identity, revision,
representation, evidence axes,
scale, resolved threshold,
measured defect or offending value/index,
capability requested
```

For block RHS incompatibility, include offending columns, per-column defects,
and thresholds. For indefiniteness, include the most negative witnessed value,
its threshold, and whether coverage was complete/structural/partial. For stale
sources, include expected and actual identity/revision. Tests should fail with
a focused report such as “scale metamorphism changed index 4 from
accepted-negative to retained-positive,” not an undifferentiated vector diff.

## 5. Core deterministic fixture bank

The same small bank should exercise every overlapping representation so that
failures can be compared directly.

### F0: zero

`0_(5 x 5)`. Diagnoses zero-scale rules, empty reduction (`0 x 5`), empty lift
(`5 x 0`), rank zero, nullity five, zero actions, and strict-solve behavior.

### F1: diagonal SPD

`diag(16, 9, 4, 1)`. Diagnoses square-root/inverse exponents and ensures the
diagonal route never invokes dense eigendecomposition.

### F2: rotated singular PSD

Construct deterministic orthogonal `Q` from a fixed Householder or QR rule and
`K = Q diag(16, 4, 1, 0, 0) Q^T`. Diagnoses action orientation, image/null
separation, pseudoinverse, strict RHS compatibility, and dense/diagonal-oracle
agreement.

### F3: repeated eigenspaces

`K = Q diag(9, 9, 1, 0, 0) Q^T`. Apply independent rotations within the
two-dimensional repeated positive space and two-dimensional null space.
Diagnoses tests that accidentally freeze eigenvector orientation.

### F4: tolerance spectrum

`c * diag(4, 1, 1e-9, 0, -1e-11)` over
`c in {1e-12, 1e-6, 1, 1e6, 1e12}` with explicit relative policies. Diagnoses
classification homogeneity and recorded thresholds.

### F5: boundary ULPs

Build eigenvalues from `tau`, `nextafter(tau, 0)`, and
`nextafter(tau, +Inf)` (and their negative counterparts) after the threshold
is resolved. Diagnoses off-by-one inequalities and accidental decimal
rounding. If a portable `nextafter` helper is needed, keep it test-local and
verify its bit-level behavior.

### F6: cancellation/conditioning

A rotated spectrum spanning a controlled condition range, without values so
small that the expected answer is unknowable in double precision. Diagnoses
unstable inverse-root/pseudoinverse actions; assertions scale by condition and
forward/backward error rather than a universal epsilon.

### F7: graph Laplacians

Connected path, disconnected union, isolated vertices, weighted graph, and a
signed-weight counterexample. Diagnose structural PSD and exact component
nullity independently from spectral routines. A weak bridge fixture separates
that algebraic fact from tolerance-relative numerical rank when the positive
spectral gap falls below or cannot be proven above `tau_rank`.

### F8: supplied factors

Tall full-rank `L`, rank-deficient `L`, permuted columns, `L U` under a
nonorthogonal change of factor coordinates, malformed dimensions, and stale
source identity. Diagnose which actions follow from `K = L L^T` and which do
not.

### F9: adversarial symmetry

The existing generalized-eigen upper-triangle trap plus scale-controlled
skew perturbations. Diagnose validation order and use the same core fixture at
the new factor boundary.

## 6. Laws and metamorphic properties

For each supported exact or repaired factor, test these laws on deterministic
blocks and a small seeded property grid:

```text
linearity:             A(aX + bY) ~= a A(X) + b A(Y)
symmetry:              <x, K y> ~= <K x, y>
quadratic energy:      ||R x||^2 ~= x^T K_r x
root composition:      root(root(x)) ~= K_r x
inverse-root pair:     root(invroot(x)) ~= P x
pseudoinverse pair:    K(K+(x)) ~= P x and K+(K(x)) ~= P x
projector:             P(P(x)) ~= P(x), P^T ~= P
complement:            P(x) + N(x) ~= x and P(N(x)) ~= 0
reduction/lift:        R(R+(z)) ~= z and R+(R(x)) ~= P x
strict solve:          K(solve(b)) ~= b only when compatibility passes
```

Metamorphic transformations:

- positive scaling `K -> c K` with zero absolute tolerances;
- simultaneous coordinate permutation `K -> Pi K Pi^T`;
- orthogonal conjugation `K -> U K U^T`;
- rotation within repeated eigenspaces;
- block partitioning/concatenation of RHS inputs;
- dense/diagonal/sparse/supplied representations where capabilities overlap;
- snapshot copy and serialize/restore for portable states;
- revision change for live sources.

Each transformation has a specific expected mapping. For example, under
`K_c = cK`, rank/projectors are unchanged, root scales by `sqrt(c)`, inverse
root by `1/sqrt(c)`, pseudoinverse by `1/c`, reduction by `sqrt(c)`, and lift
by `1/sqrt(c)`.

## 7. Numerical assertion policy

Avoid one global tolerance. Every assertion should derive a bound from the
operation, source scale, dimensions, conditioning, and recorded factor
certificate. At minimum:

- classification tests compare exact categories and recorded thresholds;
- analytic diagonal tests use tight double-precision bounds;
- reconstruction/action tests report absolute defect and a normalized
  backward-style defect;
- inverse-root/pseudoinverse tests account for the smallest retained
  eigenvalue and explicitly avoid claiming forward accuracy beyond its
  conditioning;
- projector tests use operator/Frobenius residuals with dimensions recorded;
- approximate paths, if ever admitted, compare observed error with the
  advertised bound and include a deliberately failing underreported bound.

Never loosen a tolerance simply until a test passes. A tolerance change needs
a mathematical reason, a counterexample showing the old bound was wrong, and
an assertion that the revised bound still catches a named mutation.

## 8. Mutation adequacy

The certification suite should prove that its central tests detect at least
these injected faults:

1. use `lambda` rather than `sqrt(lambda)` in the root;
2. use `Q_r` where `Q_r^T` is required in reduction;
3. classify `lambda == -tau_psd` as materially negative contrary to the frozen
   boundary (or the reverse if contract changes);
4. replace scale `s` by `max(1,s)`;
5. erase the original negative eigenvalue after clipping;
6. report a generic Gram factor as the principal square root;
7. return `K^+ b` from strict solve without checking `(I-P)b`;
8. compare repeated eigenvectors columnwise;
9. reuse a cached factor across a changed revision;
10. densify an unsupported sparse input;
11. promote user-declared or partial evidence to computed/complete;
12. omit a retained eigenvector array or native allocation from memory.

Mutation tests need not run on every CRAN check, but each mutation must be run
and recorded at the integrated certification gate. A surviving mutation is a
test-design defect, not merely a low mutation score.

## 9. Sparse non-densification and resource gates

Correct small answers do not prove a sparse path is safe. Use three layers:

1. **Dispatch evidence:** capability/route metadata says exactly which
   structural theorem or supplied factor admitted the action. Generic sparse
   storage alone cannot select an exact path.
2. **Allocation instrumentation:** counted wrappers and allocation profiling
   establish that no `n x n` dense R object or equivalent native buffer is
   retained or transiently allocated on the tested path.
3. **Peak-RSS subprocess:** a fresh R process handles a large sparse fixture
   whose dense representation exceeds a conservative memory budget. Record
   baseline, peak, input bytes, factor bytes, dimension, nonzeros, platform,
   and allocator. The bound should scale with admitted sparse/factor storage,
   not `n^2`.

Unsupported sparse actions must fail before expensive iterative probing or
dense conversion. Performance gates should assert work/allocation complexity,
not wall-clock speed. Timing may be reported diagnostically but should not be
a flaky pass/fail threshold except in separately controlled benchmarks.

## 10. Work and retained-memory certification

For every construction and action route, reconcile public work records against
an independently counted fixture:

- source/metric block calls and columns;
- setup, action/solve, and certification phases;
- factorization/eigendecomposition counters if the frozen schema adds them;
- whether counters are complete or unavailable;
- no double counting from nested operator wrappers.

Retained-memory tests must enumerate every component type: original snapshot,
spectrum, eigenvectors, diagonal, sparse factor, cached projector/action,
metadata, native handle/workspace. Verify deep-copy/immutability semantics and
that `retained_bytes()` equals the public memory record. Native bytes must not
be reported as zero merely because R cannot see them; use `NA` and
`complete = FALSE` until measured.

## 11. Test-first implementation roadmap

Tests are part of each implementation slice, not a terminal hardening pass.
The intended order is:

1. Freeze public schemas and diagnostic-condition helpers alongside failing
   or negative capability tests for every unsupported request.
2. Add analytic F0/F1 and scale/boundary F4/F5 tests before identity and
   diagonal implementation; require the exponent/orientation/boundary
   mutations to be caught.
3. Add rotated/repeated F2/F3 oracles before dense implementation; require
   source-versus-repaired defects and invariant-subspace comparisons.
4. Add action-law, block-RHS, and incompatible-solve tests before image,
   projector, root, pseudoinverse, reduction, lift, Gram, and block
   primitives.
5. Add structural theorem, unsupported-action, and memory-envelope tests
   before each admitted sparse or supplied-factor route. Admission is per
   representation/action pair, never per storage class.
6. Add identity/revision/serialization corruption cases with the first cache
   or portable factor state, reusing the 1.2 fail-closed conventions.
7. Run mutation adequacy and resource subprocesses before calling an
   implementation slice certified.
8. Run clean installed downstream conformance only after the exported surface
   is complete, then rerun the same manifest against the exact tarball.

No implementation Mote closes when its decisive tests were added only after
the code and have not been shown to catch the named mutations.

## 12. Test tiers and gates

### Fast developer tier

Runs deterministic fixture bank F0-F5, typed conditions, core laws, API
snapshots, and small representation agreement. It should be quick enough for
every focused change.

### Package tier

Runs all ordinary `testthat` tests across source and installed package paths,
including serialization, work/memory reconciliation, sparse small oracles,
and existing regression suites. The new tests must not weaken existing
generalized-SPD, plan, restart, API, or certification snapshots.

### Numerical certification tier

Runs larger seeded property grids, high-precision boundary cases where
needed, native/reference differential tests, adversarial spectra, mutation
adequacy, and all admitted representation/action pairs. It records seeds and
machine numerical metadata.

### Resource tier

Runs allocation and peak-RSS subprocess tests on each supported platform with
predeclared size/complexity bounds. It distinguishes retained memory from peak
working memory.

### Installed downstream tier

Build and install the exact eigencore candidate, then install clean
gprocrustes and DKGE conformance fixtures against public exports only. Confirm
that dependency direction remains downstream-to-eigencore and that eigencore
does not acquire application semantics. rfugw may record an explicit deferral.

### Exact artifact and hosted tier

Build one tarball, compute SHA-256 once, install that exact file in clean
libraries, run the capability manifest and certification suite, upload the
same bytes, and verify release asset hash plus tag/main/live SHA relationships.
Hosted CI evidence and local evidence are reported separately.

## 13. Capability-manifest coverage rule

The release capability manifest is the join key for testing. Every advertised
`representation x action` entry must name:

- preconditions and evidence axes;
- implementation/route label;
- source and action fidelity;
- test IDs and independent oracle;
- numerical bound or exact structural law;
- work/memory evidence;
- serialization/cache behavior;
- supported platforms and artifact test receipt.

An entry without an independent oracle or certified bound is unsupported,
even if code exists. Conversely, an unsupported entry needs a stable negative
test proving it fails before expensive computation.

## 14. Minimum acceptance for the draft-to-contract transition

Before public API freeze, reviewers should be able to answer:

1. Which test catches each tolerance inequality, action orientation, evidence
   promotion, cache-staleness, and densification defect?
2. Which oracle is independent of the implementation under test?
3. How are repeated eigenspaces compared without freezing arbitrary bases?
4. How does a failure report reveal scale, threshold, defect, source identity,
   representation, and capability?
5. Which tests prove the source was PSD, and which prove only that a repaired
   action is internally consistent?
6. Which claims require complete/structural spectrum evidence?
7. What runs per change, in the package gate, in numerical/resource
   certification, downstream, and on the exact artifact?

If any answer is “the aggregate suite is green,” the test design is not yet
diagnostic enough to freeze the contract.
